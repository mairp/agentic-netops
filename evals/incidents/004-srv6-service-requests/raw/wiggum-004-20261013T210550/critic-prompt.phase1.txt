  ```
  # Feature Specification: SRv6 Service Requests End to End
  
  **Feature Branch**: `004-srv6-service-requests`
  
  **Created**: 2026-10-11
  
  **Status**: Draft
  
  **Input**: User description: "roadmap/srv6-speckit-specify-prompt.md" (SRv6 service requests end to end, feature 004). Evidence base: `roadmap/srv6-enablement-research.md` (2026-10-11), which carries the code citations, the 21 blocking points, the work list and the owner decisions. This specification states behaviour and outcomes and cites that document for evidence.
  
  ## Context
  
  An operator who asks for a service carried over SRv6 does not get one.
  
  - Through chat, "SRv6 L3VPN ..." and "EVPN over SRv6 ..." are provisioned as
    VXLAN services (`ip-vrf` and `mac-vrf`). The word SRv6 is dropped and nothing
    tells the operator. Other SRv6 phrasings are refused.
  - An `SRv6Service` resource applied directly is accepted by the cluster and then
    stays not-Ready forever. Nothing is programmed, verified or cleaned up. Lab
    bring-up hides the failure, and the demo tutorial describes an outcome that
    does not occur.
  - No device recipe for an SRv6 VPN service has been proven on the pinned SONiC
    image.
  - The controllers' write path cannot reach the nodes of the SONiC VM lab, so on
    that lab nothing can be provisioned, the four existing constructs included.
  - The SONiC VM lab boots every switch with the same identity and no underlay.
  - The capability gate records two SRv6 checks as passed while skipping them, and
    the capability flag that should gate SRv6 is a constant.
  
  Feature 001 required SRv6 services (US5, FR-026 to FR-030, SC-013 to SC-015).
  Its 2026-09-19 reconciliation recorded them as never held and called for a
  dedicated specification (candidate C2). This is that specification. The SONiC VM
  image now in the lab has an SRv6-capable kernel dataplane and accepts SRv6
  locator and SID configuration, so the remaining gaps are in this repository
  (research, "Summary" and "Addendum 2026-10-11").
  
  **Who it is for.** A network operator asks for a tenant service between
  attachment points, carried over the SRv6 underlay, in one of three ways: in
  plain language, through the chat UI, or by applying an `SRv6Service` resource.
  The service reaches Ready only when the devices' own state shows it and client
  traffic passes. Withdrawing it releases everything it claimed. An SRv6 request
  is never provisioned over a different transport.
  
  ### Settled decisions (owner, 2026-10-11)
  
  These are givens for this specification and for its clarification step.
  
  1. Service types are L3VPN over SRv6 and EVPN over SRv6. EVPN covers routed (IP
     prefix) and bridged (MAC-VRF) services.
  2. The bridged EVPN service is conditional. If the recipe spike shows the image
     cannot carry it, it is deferred to a follow-up and requests for it are
     refused by name.
  3. The acceptance target is the SONiC VM lab. Client-to-client traffic is
     required; control-plane state alone is not acceptance.
  4. `SRv6Service` stays a separate resource kind. The upstream Kubenet `Network`
     field names do not change.
  5. Path steering is in scope in one form: a service may name a preferred spine
  ```

  ```
  # run_proof <expected-rc> <args...>: run proof.sh with an isolated PROOF_DIR.
  run_proof() {
      local expect="$1"
      shift
      local out rc
      out="$(PROOF_DIR="$WORK/proofs" bash "$PROOF_SH" "$@" 2>&1)"
      rc=$?
      printf '%s' "$out" > "$WORK/last-output"
      LAST_RC="$rc"
      if [[ "$rc" != "$expect" ]]; then
          echo "FAIL: proof.sh $* -> exit $rc (expected $expect)" >&2
          echo "$out" >&2
          FAIL=$((FAIL + 1))
          return 1
      fi
      return 0
  }
  
  check() { # check <description> <condition...>
      local desc="$1"
      shift
      if "$@"; then
          PASS=$((PASS + 1))
      else
          echo "FAIL: $desc" >&2
          FAIL=$((FAIL + 1))
      fi
  }
  ```

# Contract: fabric-executor transport per node kind

The fabric-executor stays the only southbound and stays a host service. Its HTTP API
(`/v1/node/apply`, `/v1/node/verify`, `/v1/nodes`, `/healthz`) does not change shape. What changes
is how a command reaches the node.

## 1. Interface

```go
type transport interface {
    // run executes argv on the node and returns stdout, stderr and an error
    // that is nil only for exit code 0.
    run(ctx context.Context, argv []string, stdin []byte) (stdout, stderr string, err error)
    kind() string // "docker" | "ssh"
}
```

Today every command goes through `(*server).exec` (`cmd/fabric-executor/main.go:663`). That
function becomes the `docker` implementation, unchanged in behaviour. The server resolves a
transport per node and no caller knows which one it got.

## 2. Selection

| Env | Shape | Meaning |
| --- | --- | --- |
| `FABRIC_NODE_MAP` | `{"leaf01":"clab-...-leaf01", ...}` | unchanged: logical node to container |
| `FABRIC_NODE_TRANSPORT` | `{"leaf01":{"kind":"ssh","addr":"172.31.0.21","user":"admin"}, ...}` | optional; a node absent here uses `docker` |
| `FABRIC_SSH_KEY` | path | private key, mode 0600; required if any node is `ssh` |
| `FABRIC_SSH_KNOWN_HOSTS` | path | per-lab host keys; required if any node is `ssh` |
| `FABRIC_PROBE_MAP` | `{"leaf01/wan1":"clab-...-srv6-client01", ...}` | attachment to probe container (§4) |

`scripts/provision.sh` builds `FABRIC_NODE_TRANSPORT` from each node container's `clab-node-kind`

## 1. Entry point

```go
func ForSRv6Service(svc *v1alpha1.SRv6Service, alloc Allocations, opts Options) (*Plan, error)
```

# Contract: operator phrasings accepted, clarified and refused

What the tier does with a request that names SRv6. Every row is a corpus case under
`agents/tests/corpus/phrasings/`. The vocabulary, the guard
(`agents/tests/unit/test_vocabulary_guard.py`) and the refusal texts change in the same change

"Supported" below means a member of the supported set ([data-model.md](../data-model.md) §3).

## 1. Recognition

A request is an SRv6 request when it matches, case-insensitively, any of: `srv6`,
`segment routing v6`, `segment routing over ipv6`, `segment-routing v6`,
`segment-routing over ipv6`. A bare "segment routing" does not name SRv6 and is left to the
existing patterns, so a refusal never says a request named SRv6 when it did not. Recognition runs before
`_detect_service_type` and before the `l3vpn`, `evpn` and `vrf` patterns
(`agents/provisioning/mapper/agent.py:67-82`). The SRv6 qualifier decides the transport; a legacy
service name beside it is never enough to select a VXLAN construct.

| Request names | Interpretation |
| --- | --- |
| `ip-vrf over srv6`, `SRv6 ip-vrf`, `SRv6 L3VPN` (migration alias), `routed service over srv6` | `ip-vrf`, transport `srv6`, signalling `vpn` |
| `ip-vrf over srv6 with evpn signalling`, `routed EVPN over SRv6` | `ip-vrf`, transport `srv6`, signalling `evpn` |
| `mac-vrf over srv6`, `bridged EVPN over SRv6`, `extend vlan N over srv6` | `mac-vrf`, transport `srv6`, signalling `evpn` |
| `EVPN over SRv6` with no construct and no "routed"/"bridged" | clarification C2 |
| `SRv6 service` with no construct | clarification C1 |

How the tier restates the request to the operator (the only forms shown on operator surfaces):
`ip-vrf over srv6`, `ip-vrf over srv6 with evpn signalling`, `mac-vrf over srv6` (spec FR-013).

  per variant carries the variant (`q5-ip-vrf-vpn-apply`), and a proof taken again later carries a
  suffix (`-default`, `-us4`, `-final`) so that it never overwrites the capture an earlier gate
  rested on.
- `.wiggum/` is not tracked. A proof is a local artefact; what makes it evidence is that its
  `.cmd` regenerates its `.out` on the live lab. The tracked index
