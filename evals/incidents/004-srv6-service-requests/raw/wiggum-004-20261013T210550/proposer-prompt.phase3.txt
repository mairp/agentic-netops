# Contract: fabric-executor transport per node kind

The fabric-executor stays the only southbound and stays a host service. Its HTTP API
(`/v1/node/apply`, `/v1/node/verify`, `/v1/nodes`, `/healthz`) does not change shape. What changes
is how a command reaches the node.

## 1. Interface

```go
type transport interface {
    // run executes argv on the node and returns stdout, stderr and an error
    // that is nil only for exit code 0.
    run(ctx context.Context, argv []string, stdin []byte) (stdout, stderr string, err error)
    kind() string // "docker" | "ssh"
}
```

Today every command goes through `(*server).exec` (`cmd/fabric-executor/main.go:663`). That
function becomes the `docker` implementation, unchanged in behaviour. The server resolves a
transport per node and no caller knows which one it got.

## 2. Selection

| Env | Shape | Meaning |
| --- | --- | --- |
| `FABRIC_NODE_MAP` | `{"leaf01":"clab-...-leaf01", ...}` | unchanged: logical node to container |
| `FABRIC_NODE_TRANSPORT` | `{"leaf01":{"kind":"ssh","addr":"172.31.0.21","user":"admin"}, ...}` | optional; a node absent here uses `docker` |
| `FABRIC_SSH_KEY` | path | private key, mode 0600; required if any node is `ssh` |
| `FABRIC_SSH_KNOWN_HOSTS` | path | per-lab host keys; required if any node is `ssh` |
| `FABRIC_PROBE_MAP` | `{"leaf01/wan1":"clab-...-srv6-client01", ...}` | attachment to probe container (§4) |

`scripts/provision.sh` builds `FABRIC_NODE_TRANSPORT` from each node container's `clab-node-kind`
label. The executor refuses to start if a node is `ssh` and the key or known-hosts file is missing
or has wider permissions than 0600.

# Contract: fabricplan operations and checks for SRv6

`pkg/fabricplan` renders an `SRv6Service` into per-node `Ops`, `Checks` and `Rollback`, in the
vocabulary the fabric-executor already speaks (`pkg/fabricplan/plan.go:53-95`). No new op class
is added. One new check type is added (§2).

## 1. Entry point

```go
func ForSRv6Service(svc *v1alpha1.SRv6Service, alloc Allocations, opts Options) (*Plan, error)
```

- Pure: no I/O, deterministic output for identical input. `plan_test.go` asserts byte-identical
  JSON across runs.
- `alloc` carries every identifier; the renderer generates none.
- `opts` carries the site port map, node kinds and each node's bootstrap-owned locator.
- One `NodePlan` per attachment node. A steered service may also need state on the ingress leaf
  only; it never renders ops for a spine.
- The renderer never emits an op that creates, changes or removes a locator. A unit test fails if
  any op touches the locator table or the FRR locator block.

## 2. New check type

| Type | Fields | Passes when |
| --- | --- | --- |
| `probe-ping` | `probeFrom`, `probeTo`, `addr`, `size`, `count` | the probe host for `probeFrom` reaches `addr` with `count` echoes of `size` bytes, don't-fragment set |

Executed by the executor in the client container registered for the attachment
([executor-transport.md](./executor-transport.md) §4). It is used once, at first activation, and
is not part of the periodic per-node checks.

# Contract: operator phrasings accepted, clarified and refused

What the tier does with a request that names SRv6. Every row is a corpus case under
`agents/tests/corpus/phrasings/`. The vocabulary, the guard
(`agents/tests/unit/test_vocabulary_guard.py`) and the refusal texts change in the same change
(FR-018).

"Supported" below means a member of the supported set ([data-model.md](../data-model.md) §3).

## 1. Recognition

A request is an SRv6 request when it matches, case-insensitively, any of: `srv6`,
`segment routing v6`, `segment routing over ipv6`, `segment-routing v6`,
`segment-routing over ipv6`. A bare "segment routing" does not name SRv6 and is left to the
existing patterns, so a refusal never says a request named SRv6 when it did not. Recognition runs before
`_detect_service_type` and before the `l3vpn`, `evpn` and `vrf` patterns
(`agents/provisioning/mapper/agent.py:67-82`). The SRv6 qualifier decides the transport; a legacy
service name beside it is never enough to select a VXLAN construct.

| Request names | Interpretation |
| --- | --- |
| `ip-vrf over srv6`, `SRv6 ip-vrf`, `SRv6 L3VPN` (migration alias), `routed service over srv6` | `ip-vrf`, transport `srv6`, signalling `vpn` |
| `ip-vrf over srv6 with evpn signalling`, `routed EVPN over SRv6` | `ip-vrf`, transport `srv6`, signalling `evpn` |
| `mac-vrf over srv6`, `bridged EVPN over SRv6`, `extend vlan N over srv6` | `mac-vrf`, transport `srv6`, signalling `evpn` |
| `EVPN over SRv6` with no construct and no "routed"/"bridged" | clarification C2 |
| `SRv6 service` with no construct | clarification C1 |

How the tier restates the request to the operator (the only forms shown on operator surfaces):
`ip-vrf over srv6`, `ip-vrf over srv6 with evpn signalling`, `mac-vrf over srv6` (spec FR-013).

# Quickstart: validating SRv6 Service Requests End to End (004)

One scenario per acceptance criterion. Each names the command that produces its proof.

**Rules for every proof**

- A proof is a capture taken on the live lab through `scripts/proof.sh <name> -- <command>`,
  which stores the exact command in `<name>.cmd` and its output and exit code in `<name>.out`
  under `.wiggum/features/004-srv6-service-requests/gates/proofs/`. Re-running `<name>.cmd` must
  regenerate `<name>.out` (FR-039, SC-015).
- A scenario marked **cannot be shown yet** has no runnable proof command today. It says what is
  missing instead of describing an expected result.
- `scripts/proof.sh` is the first thing Phase 0 builds; until then no scenario here is runnable.
- Proof names: `tasks.md` is the naming source. The names below are patterns; a scenario run once
  per variant carries the variant (`q5-ip-vrf-vpn-apply`), and a proof taken again later carries a
  suffix (`-default`, `-us4`, `-final`) so that it never overwrites the capture an earlier gate
  rested on.
- `.wiggum/` is not tracked. A proof is a local artefact; what makes it evidence is that its
  `.cmd` regenerates its `.out` on the live lab. The tracked index
  `docs/SRV6_ACCEPTANCE_004.md` cites proofs by name.
- Packets: IPv6 probes use a payload of 8900 bytes with don't-fragment set, below the ~9120-byte
  effective payload under MTU 9216 with an SRv6 header; plus one default-size probe. The exact
  size is confirmed in Phase 0 ([data-model.md](./data-model.md) §8.7).
- Commands that run on a switch go through `node_run` from
  `tests/integration/lib/node_exec.sh`, so they work on both profiles.

## If this phase depends on a job that cannot finish inside one pass: YIELD
Do NOT sleep, poll, tail, or `until ... done` your way through a long job.
Waiting inside a pass costs a full context rebuild per pass and gets the pass
killed at the ceiling — which also kills the job, because a job you start from
your own Bash tool lives in the pass's process tree.
Instead, END THE PASS and let specstride do the waiting with no model session open.
Write this file ATOMICALLY (tmp then `mv`), then STOP without writing evidence:
  /root/agentic-netops/.wiggum/features/004-srv6-service-requests/yield/phase3-attempt1-20261013-120241-4145257.json
```json
{"contract": "specstride-pass-yield/v1",
 "reason": "one line: what you are waiting on and why the evidence needs it",
 "job": {"mode": "launch", "argv": ["/usr/bin/make", "live"], "cwd": "/root/agentic-netops"},
 "resume_when": {"kind": "exit_code_file"},
 "deadline_sec": 7200,
 "on_resume": "exactly what the next pass should do with the result"}
```
- `job.mode`: "launch" (PREFERRED — specstride starts it in its own session, where no
  pass kill can reach it) or "adopt" with `pid: N` if you already started it
  under `setsid`. An adopt naming a pid in this pass's own session is REFUSED.
- `resume_when.kind`: exit_code_file (defaults to the rc file specstride writes for a
  job it launched) | pid (defaults to the job it launched) | file_exists |
  file_stable (+ `stable_sec`) | grep (+ `path`, `pattern`).
- `deadline_sec` is REQUIRED — the run holds this workdir for the whole wait.
- `on_resume` is handed back to you verbatim next pass, with the job's exit code
  and a bounded slice of its log. Say what you will do with them.
A yield is not a failure: it does not count as an error, it is not a stall, and
by default it does not even burn an iteration. Yielding on a 90-minute job is
the CORRECT move; waiting for it inside the pass is the expensive one.
