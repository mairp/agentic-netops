  // RenderBatch validates a batch all-or-nothing and returns one YAML document per
  // valid service in the input order. On validation failure, returns a ValidationError
  // with aggregated causes and no output documents.
  func RenderBatch(inputs []ServiceInput) ([]string, error) {
  	// Detect duplicates
  	ids := map[string]int{}
  	for i, in := range inputs {
  		if _, ok := ids[in.ServiceID]; ok {
  			ids[in.ServiceID] = -1
  		} else {
  			ids[in.ServiceID] = i
  		}
  	}
  	var causes []string
  	for i := range inputs {
  		in := inputs[i]
  		dup := false
  		if idx, ok := ids[in.ServiceID]; ok && idx == -1 { dup = true }
  		if err := in.ValidateAllOrNothing(i, dup); err != nil {
  			if ve, ok := err.(*ValidationError); ok {
  				causes = append(causes, ve.Causes...)
  			} else {
  				causes = append(causes, err.Error())
  			}
  		}
  	}
  	if len(causes) > 0 {
  		return nil, &ValidationError{Causes: causes}
  	}
  	out := make([]string, 0, len(inputs))
  	for i := range inputs {
  		in := inputs[i]
  		bundle, err := Translate(&in)
  		if err != nil { return nil, err }
  		out = append(out, bundle.NetworkYAML)
  	}
  	return out, nil
  }
  
  // MarshalError produces a deterministic JSON string for structured validation errors.
  // It disables HTML escaping so comparison substrings like ">=1" remain readable
  // and stable in tests and CLI output.
  func MarshalError(err error) string {
  	if err == nil { return "" }
  	m := map[string]any{"error": "validation"}
  	if ve, ok := err.(*ValidationError); ok {
  		m["causes"] = ve.Causes
  	} else {
  		m["causes"] = []string{err.Error()}
  	}
  	// Use an Encoder with HTML escaping disabled to avoid sequences like \u003e
  	// for '>' which make human/fixture comparison brittle.
  	var buf bytes.Buffer
  	enc := json.NewEncoder(&buf)
  	enc.SetEscapeHTML(false)
  	enc.SetIndent("", "  ")
  	_ = enc.Encode(m)
  	// json.Encoder adds a trailing newline; trim it for stable output.
  	out := buf.String()
  	if len(out) > 0 && out[len(out)-1] == '\n' { out = out[:len(out)-1] }
  	return out
  }

# Feature Specification: AINETOPS SONiC EVPN/VXLAN Fabric

**Feature Branch**: `001-ainetops-sonic-evpn-fabric`  
**Created**: 2026-08-28  
**Status**: Draft  
**Input**: Replace the former vendor-specific router/MPLS use case with a fully open-source,

## Scope and interpretation

"Replace a Cisco router with SONiC" means replace its **logical role and supported service
intent** with a SONiC leaf, border leaf, or spine. It does not mean SONiC can run on arbitrary
router hardware or that every WAN/MPLS feature has an EVPN equivalent. The MVP covers a
containerlab fabric and only the mappings listed in this specification. It contains no
Crosswork, NSO, CNC, proprietary NED, or vendor-specific controller dependency.

# Contract: Kubernetes APIs and Generated Resources

**Applies to**: Kubenet/KUID resources, required `SRv6Service`, optional `MigrationPlan`,
provider-generated SDC resources, status, ownership, and version compatibility.

## API boundary

1. Users express ongoing fabric/service intent with the pinned upstream Kubenet `Network` API.
2. KUID owns identifier/address allocation through its upstream claim APIs.
3. Kubenet derives upstream `NetworkDevice` objects.
4. `ainetops-sonic-provider` creates upstream SDC `Config` resources.
5. SDC is the only component authorized to mutate device configuration.
6. The required AINETOPS `SRv6Service` expresses only SRv6 endpoint/path/behavior intent;
   KUID owns its locator/SID claims and SDC owns its device transactions.
7. The optional AINETOPS `MigrationPlan` records source translation and cutover evidence; it
   does not replace `Network`, `NetworkDevice`, or `Config`.

All APIs and their controllers run in the named Kind cluster. Containerlab is not an
application runtime and hosts only network/endpoint nodes.

## Deployment contract

- `config/kind/cluster.yaml` is the declarative Kind cluster definition; its config API,
  cluster name, node roles, node image digest, pod/service CIDRs, mounts, labels, and port
  mappings are version controlled.
- `scripts/provision.sh` is the sole implementation of complete environment creation and
  convergence. Make/CI commands may invoke it but may not reimplement its phases.
- `scripts/off.sh` is the sole implementation of environment shutdown and cleanup.
- Every platform application is installed into Kind with pinned Kubernetes manifests or Helm
  releases. Standalone application containers and Compose files are contract violations.
- Namespaces, Services, PVCs, Secrets, RBAC, monitoring discovery, dashboards, datasources,
  and alert rules are Kubernetes resources.
- Kind nodes and containerlab management interfaces share a dedicated labeled Docker network;
  pod and service CIDRs do not overlap it.
- Lifecycle scripts resolve the exact cluster, topology, and network targets and refuse broad
  or unowned deletion.

## Version contract

- Pin one complete Kubenet/KUID release or commit, including CRDs, controllers, examples, and
  provider input schemas.
- Pin one SDC release and install only its matching CRDs/controllers.
- Pin one containerlab release and immutable SONiC image digest per lab profile.
- Pin one SONiC/OpenConfig YANG schema commit and provider mapping version per SONiC image.
- Pin gNMIc, the gNMI-path/label mapping, Grafana Flow plugin, and generated topology-asset
  schema with the observability stack.
- Publish the five-part compatibility set in deployment metadata and provider status.
- A mismatch MUST set `SchemaMismatch`, emit no changed SDC spec, and leave the last known
  valid applied intent intact.
- `latest`, floating branches, and a mixture of Kubenet tutorial/main API shapes are forbidden.

# Contract: Translation, Reconciliation, and Safety

**Applies to**: Migration translation, the AINETOPS SONiC provider, SDC integration, device
application, drift, failure, and deletion.

## Rule 1: No silent semantic loss

- A mapping is allowed only when every required source property has a qualified target
  equivalent.
- Limited equivalence, such as VPWS represented by a dedicated L2VNI, requires explicit opt-in
  and a durable status finding.
- Unsupported fields reject the entire migration plan before allocations, generated Network,
  or SDC Config mutation.
- Raw device CLI is never an accepted source format.

## Rule 2: Deterministic, idempotent rendering

- Equivalent normalized input, topology, allocations, schema, and mapping version produce
  byte-equivalent canonical SDC intent.
- Resource names, ordering, and hashes are stable.
- An unchanged render results in no Kubernetes spec write and no gNMI Set.
- Rendering has no hidden external allocation or mutable local state.

## Rule 3: Dependency gates precede mutation

The provider does not emit changed device intent until:

1. source intent and references are valid;
2. topology and all required allocations are Ready;
3. the target and credentials are Ready;
4. image/schema/mapping compatibility matches;
5. every rendered path passes offline/schema validation.

Failure sets a current-generation condition and Event. Partial render output is not applied.

## Rule 4: One owner per managed path

- Kubenet/KUID owns intent and allocations; provider owns generated Config specs; SDC owns
  device transactions.
- Provider uses scoped paths and server-side apply field ownership.
- AINETOPS does not overwrite unmanaged device paths.
- Conflicting ownership or intent priority is a terminal error until explicitly resolved.

## Rule 5: Safe transaction and readiness semantics

- SDC validation and transaction confirmation are mandatory; direct device mutation is
  forbidden.
- Aggregate `Ready=True` requires all mandatory per-device operations to be confirmed.
- A mixed success/failure result is `Degraded`, records every target, and never claims full
  success.
- The last valid configuration remains desired when a new generation fails validation.
- No automated rollback may erase unrelated, shared, or manually owned configuration.

## Rule 6: Drift is explicit

- SDC compares intended and running configuration for owned paths.
- Lab mode uses documented revertive behavior and verifies restoration.
- Unmanaged-path changes are observed only if subscribed; they are not reverted or claimed.
- Production drift policy must be explicitly selected and cannot inherit lab defaults silently.

## Rule 7: Bounded retry and classified errors

- Transient transport/unavailability failures retry with bounded exponential backoff and jitter.
- Terminal schema, unsupported-feature, ownership, collision, and compatibility errors do not
  hot-loop; they retry on relevant generation or dependency change.

# Research: AINETOPS Open-Source SONiC Orchestration

**Feature**: AINETOPS SONiC EVPN/VXLAN Fabric

**Method**: Independent research agents reviewed the former specification and current official

## Executive decision

Use the smallest declarative control plane that preserves clear ownership:

```text
Git or kubectl
      │
      ▼
Kubernetes API
      ├── Kubenet topology + Network intent
      ├── KUID inventory and identifier claims
      ├── required SRv6Service
      └── optional MigrationPlan (audit/cutover only)
                         │
                         ▼
               Kubenet NetworkDevice
                         │
                         ▼
              ainetops-sonic-provider
                         │
                         ▼
                SDC Config / ConfigSet
                         │  YANG validation + transaction + drift
                         ▼
                 gNMI / JSON_IETF
                         │
                         ▼
            containerlab SONiC leaf/spine fabric
```

This deliberately avoids a second workflow engine. Kubernetes reconciliation is the workflow;
Kubenet/KUID owns abstract intent and allocation; the AINETOPS provider owns only rendering;
SDC owns schema-aware target transactions and running-state comparison.

## Decision 1: Reuse Kubenet/KUID instead of defining fabric CRDs

- **Decision**: Pin and reuse Kubenet `Topology`, design/config, `Network`, and
  `NetworkDevice` APIs plus KUID IP/ASN/VLAN/VNI index and claim APIs.
- **Rationale**: Kubenet is explicitly designed to use Kubernetes as a declarative,
  continuously reconciled NOS automation system. Its published examples already model a
  default underlay plus bridged EVPN, routed EVPN, and IRB networks, then derive per-device
  `NetworkDevice` objects and SDC `Config` objects.
- **Important version finding**: The v0.0.1 tutorial uses `NetworkConfig` and fields such as
  `bridgeDomains`/`routingTables`; newer bundled artifacts may expose `NetworkDesign` and
  `bridges`/`routers`. Implementation must pin one complete commit/release and validate every
  example against that release's CRDs. It must not combine tutorial YAML with unpinned main.
- **Alternative rejected**: A new `Fabric`, `Tenant`, `VRF`, and `Attachment` CRD family would
  duplicate the upstream intent model and create ambiguous ownership.
- **Sources**: [Kubenet purpose and components](https://learn.kubenet.dev/),
  [network configuration](https://learn.kubenet.dev/02-examples/04_networkconfig/),
  [default network](https://learn.kubenet.dev/02-examples/05_defaultnetwork/),
  [bridged EVPN](https://learn.kubenet.dev/02-examples/06_bridgednetwork/),
  [routed EVPN](https://learn.kubenet.dev/02-examples/07_routednetwork/), and
  [IRB](https://learn.kubenet.dev/02-examples/08_irbnetwork/).
