     1	# Quickstart: Validate the AINETOPS SONiC Fabric
     2	
     3	**Feature**: AINETOPS SONiC EVPN/VXLAN Fabric  
     4	**Purpose**: Acceptance workflow the implementation MUST make executable. Commands name the
     5	planned stable targets; their implementation is tracked in [tasks.md](./tasks.md).
     6	
     7	## Prerequisites
     8	
     9	- Linux host with the CPU/RAM/disk documented in the implementation README.
    10	- Docker-compatible runtime and permission to launch privileged network containers.
    11	- `kind`, `kubectl`, `helm`, `containerlab`, `jq`, `curl`, `tcpdump`, and a gNMI client at
    12	  versions checked by `versions.lock.yaml`.
    13	- KVM/nested virtualization only when the `sonic-vm` conformance profile is selected.
    14	- A locally imported immutable SONiC image whose digest matches `versions.lock.yaml`.
    15	- No production credentials; lab credentials/certificates are generated into Kubernetes
    16	  Secrets and removed during teardown.
    17	
    18	## 1. Provision the complete environment
    19	
    20	```bash
    21	./scripts/provision.sh --profile sonic-vs --cluster-name ainetops
    22	```
    23	
    24	This is the primary and idempotent lifecycle command. It performs:
    25	
    26	- pin and host preflight validation;
    27	- creation of the dedicated labeled Docker management network;
    28	- creation of the pinned Kind cluster and attachment of its nodes to that network;
    29	- SONiC capability qualification for the selected profile;
    30	- deployment of the eight-node containerlab topology;
    31	- installation inside Kind of Kubenet/KUID, SDC, the AINETOPS provider/translator, OTel
    32	  Collector, Prometheus, Grafana, Prometheus Operator resources, and gNMIc;
    33	- application of schemas, discovery, topology, allocation pools, and default fabric intent;
    34	- bounded waits for all required readiness gates.
    35	
    36	Expected: the command completes without an undocumented manual step. Running the same command
    37	again reports convergence and does not recreate the cluster, churn application releases, or
    38	issue unchanged device configuration.
    39	
    40	If the fast profile fails its unmodified capability gate, use:
    41	
    42	```bash
    43	./scripts/off.sh --cluster-name ainetops
    44	./scripts/provision.sh --profile sonic-vm --cluster-name ainetops
    45	```
    46	
    47	The gate verifies:
    48	
    49	- gNMI Capabilities, Get, Set, and Subscribe;
    50	- authentication/TLS and JSON_IETF encoding;
    51	- persistent writable configuration;
    52	- all YANG paths the provider needs;
    53	- BGP EVPN/VXLAN services and required route behavior.
    54	- IPv6 underlay forwarding, SRH processing, H.Encaps.Red, transit End, End.DT46, SID-list/
    55	  steering programming, `sonic-srv6` gNMI Set/Get, and MySID counters.
    56	
    57	The conformance suite MUST NOT skip a failed capability.
    58	
    59	## 2. Verify Kind and centralized applications
    60	
    61	```bash
    62	kind get clusters
    63	kubectl cluster-info --context kind-ainetops
    64	kubectl get pods -A
    65	kubectl get helmreleases -A 2>/dev/null || helm list -A
    66	```
    67	
    68	Expected: the `ainetops` Kind cluster exists and every required application is Ready inside it.
    69	No Kubenet, SDC, AINETOPS, OTel, Prometheus, Grafana, or gNMIc application container runs as a
    70	standalone host/Compose workload.
    71	
    72	The functional namespaces are fixed in deployment manifests, for example `ainetops-system`,
    73	`sdc-system`, `kubenet-system`, and `monitoring`; the selected upstream release may add its own
    74	documented namespaces.
    75	
    76	## 3. Verify the external containerlab fabric
    77	
    78	```bash
    79	containerlab inspect --topo lab/topology.clab.yml
    80	kubectl get topology -A
    81	```
    82	
    83	Expected nodes: `spine01`, `spine02`, `leaf01`, `leaf02`, `client01`, `client02`,
    84	`srv6-client01`, and `srv6-client02`. Each leaf has one link to each spine, one EVPN client,
    85	and one SRv6 client attachment. The implementation documents
    86	the exact resource name for the pinned topology CRD if its short name differs. Kind nodes and
    87	SONiC management interfaces share only the dedicated AINETOPS management network; pod/service
    88	networks remain separate.
    89	
    90	## 4. Onboard SONiC through SDC
    91	
    92	```bash
    93	make sdc-onboard
    94	make wait-targets
    95	```
    96	
    97	Inspect the exact pinned SDC resources:
    98	
    99	```bash
   100	kubectl get schemas.inv.sdcio.dev -A
   101	kubectl get targets.config.sdcio.dev -A
   102	```
   103	
   104	Expected: one Ready schema matching the image and four Ready SONiC targets. Connection and
   105	sync profiles reference Secrets; plaintext credentials do not appear in manifests or status.
   106	
   107	## 5. Reconcile the default fabric
   108	
   109	```bash
   110	kubectl apply -f examples/fabric/
   111	make wait-fabric
   112	make verify-fabric-control-plane
   113	```
   114	
   115	Expected:
   116	
   117	- KUID claims for loopbacks, `/31` links, ASNs, VLAN/VNI pools become Ready;
   118	- Kubenet derives `NetworkDevice` resources for the default Network;
   119	- provider-generated SDC Config resources are Validated, Applied, and Ready;
   120	- every leaf-spine underlay adjacency and required EVPN session is established;
