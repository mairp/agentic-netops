     1	# AINETOPS Operators Guide
     2	
     3	Applies to: specs/001-ainetops-sonic-evpn-fabric
     4	
     5	This document provides operator-facing procedures and acceptance expectations for the AINETOPS SONiC EVPN/VXLAN Fabric reference.
     6	
     7	Contents:
     8	- Compatibility matrix and pins
     9	- Resource sizing
    10	- Image acquisition

    14	
    15	## Compatibility matrix and pins
    16	
    17	All platform versions are pinned in versions.lock.yaml and verified by make verify-compat.
    18	- Kubernetes, controller-runtime, Go toolchain
    19	- Kubenet/KUID release and commit (single API shape)
    20	- SDC (core/config-server/schema-server releases)
    21	- Containerlab version
    22	- SONiC images (sonic_vs, optional sonic_vm) and their YANG compatibility
    23	- Tooling images (gNMIc, OTel Collector, Prometheus, Grafana, Flow plugin) pinned by digest
    24	
    25	See: versions.lock.yaml
    26	Run: make verify-compat
    27	
    28	## Resource sizing
    29	
    30	Reference lab (8 SONiC nodes + 4 Linux endpoints):
    31	- Host CPU: 8 vCPU minimum (16 recommended)
    32	- Host Memory: 16 GiB minimum (32 GiB recommended)
    33	- Disk: 40 GiB free (logs, images, PVCs)
    34	- Kind cluster: 1 control-plane node
    35	- Prometheus PVC: 5 GiB (configurable)
    36	
    37	Preflight enforces minimal CPU/RAM/disk and tool versions.
    38	
    39	## Image acquisition
    40	
    41	- SONiC VS: import the pinned container image (versions.lock.yaml.sonic_images.sonic_vs.image)
    42	- SONiC VM (optional conformance profile): build via vrnetlab and record digest in versions.lock.yaml; requires KVM (/dev/kvm) and nested virtualization
    43	- All other platform images are pulled by Kubernetes from pinned digests
    44	
    45	## EVPN/SRv6 mapping limitations
    46	
    47	- VPWS/E-Line is represented by a dedicated 2-attachment L2VNI; full pseudowire/RFC 8214 feature parity is NOT claimed
    48	- RSVP-TE, SR-MPLS policies, pseudowire OAM/control-word, multicast VPN, and complex QoS/OAM are unsupported
    49	- Only qualified YANG paths are rendered; unsupported fields reject the translation before any device change
    50	
    51	## Telemetry pipeline and topology presentation
    52	
    53	- gNMIc runs in-cluster and subscribes to SONiC targets; it exports OTLP to the OTel Collector
    54	- OTel Collector normalizes and exports to Prometheus (in-cluster metrics store)
    55	- Grafana consumes Prometheus and the generated topology ConfigMap (monitoring/ainetops-topology) to render orchestration, pipeline health, and topology views
    56	
    57	See manifests under deploy/observability/ and deploy/gnmi/
    58	
    59	## Recovery procedures
    60	
    61	- Idempotence: re-run scripts/provision.sh to converge to Ready; unchanged intent results in no SDC spec write (verified by tests)
    62	- Partial failures: controllers surface Degraded and exact target errors; recover by fixing cause and re-running provision
    63	- Teardown: scripts/off.sh is safe from any partial state; it removes the containerlab lab, optionally deletes the Kind cluster, removes the owned Docker network, and cleans up lab-generated secrets
    64	
    65	## Break-glass finalizer procedure
    66	
    67	Controllers add ainetops.dev/finalizer to owned resources to delete downstream SDC intent first. If a controller or the API becomes permanently broken, an operator may break-glass:
    68	
    69	1) Inspect finalizers:
    70	   kubectl get networkdevices.network.kubenet.dev -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name} {.metadata.finalizers}\n{end}'
    71	
    72	2) Remove the finalizer explicitly acknowledging loss of managed cleanup:
    73	   kubectl -n <ns> patch networkdevice <name> --type=json -p='[{"op":"remove","path":"/metadata/finalizers"}]'
    74	
    75	This skips ordered deletion of SDC intent and should be followed by a manual cleanup of any residual SDC Config resources.
